## Item 1 — Meeting-room dock/undock bug + REAL Chrome screen share
User report: "dock/undock is buggy at the meeting room — it doesn't let me undock, it says I am docked but clicking redocks… and by docking I meant it lets me share my **real screen through Chrome**."

### Root causes (diagnosed — verify each, note if the real cause differs)
1. `web/game.js` `handleInteraction()` (line ~472): while `this.projectorDocked` is true, pressing **E near the projector opens the SETTINGS projector modal** (`toggleProjectorModal(true)`) instead of undocking. There is no E-undock path, so the user's only undock options are the modal's `undockBtn` or walking away — which feels like it "won't undock / redocks."
2. `web/game.js` auto-undock (line ~579-583): walking >45px away calls `handleProjectorUndock()`, but that only sets `projectorPresenter = null` locally — it does NOT clear the local `this.projectorDocked` flag or broadcast the undock, so the local player's own "docked" state can stick.
3. The docked screen is currently a **fake stylized panel**, not a real share.

### Required behavior (the fix)
- **E near the projector toggles dock state directly:**
  - not docked + near → dock (request screen share).
  - docked + near → **undock** (stop share). Do NOT open the settings modal from the E key. The settings modal (topic/preset buttons) should open from a **separate small "⚙ Present" button** on the projector interact prompt, or from clicking the projector while already docked via a distinct control — not the E key.
- **Auto-undock on walk-away** must also clear local `this.projectorDocked` and broadcast `projector-undock`, and must stop the local shared stream.
- **Handle the stream being stopped externally** (browser "Stop sharing" control, or the tab losing focus): listen to the `stream.getTracks().on('stop')` and on `window` visibility/blur; when the shared stream stops, auto-undock + broadcast so no one is left "stuck docked."
- **REAL screen share (the headline ask):** when the docked player docks, call `navigator.mediaDevices.getDisplayMedia({ video: { frameRate: 15 } })`. Render that stream into the projector modal's canvas (replace the fake stylized panel): an `<img>`/`<video>` with `object-fit: contain` filling the projector screen area, plus the topic bar. When undocked or the stream stops, show a "No presentation" placeholder.
  - If `getDisplayMedia` is unavailable or the user cancels the picker → show a "Screen share cancelled — still docked, showing placeholder" state and let them retry; do NOT crash or leave the dock stuck.
  - The **remote** (other players) view: keep the single-occupant server logic (`server.js` line ~1489). For remote rendering, replace the fake panel with a canvas that shows the presenter's name + topic + a "screen not viewable in this demo build" placeholder — full WebRTC screen streaming to other clients is OUT OF SCOPE for this fix (note it in the report as a future item). What must work end-to-end: single-occupant enforcement, busy toast, dock/undock state sync, and the docked player seeing their OWN real shared screen.
- **Sync:** keep `server.js` projector presenter broadcast (line ~1496) and `net.js` `sendProjectorDock`/`sendProjectorUndock` (lines ~142-147). Add a `screen-share-active` flag to the presenter payload so remote players know whether a real share is live (for the placeholder vs. "live" indicator). No server protocol changes needed beyond the flag.

### Verification (add tests)
- Dock → E again → undocks (state clears, stream stops).
- Walk away while docked → undock broadcasts, local `projectorDocked` false.
- Cancel the getDisplayMedia picker → dock not stuck, placeholder shown, can retry.
- Second player dock attempt → `projector-busy` toast, presenter unchanged.

## Item 3 — Typing board: typing 'e' closes the board
User report: "I can't type an e on the typing board without closing it."

### Root cause (diagnosed)
The global `window` `keydown` handler (`web/game.js` `setupInput()`, line ~231) has **no guard for when focus is inside a text input**. Typing `e` in `#typingBoardInput` fires the global `e` branch (line ~269) → `handleInteraction()`, which opens/closes the projector modal. The same latent bug affects the presenter topic input (`#presenterTopicInput`) and the drink-station preset name input.

### Required behavior
- At the top of the global `keydown` handler, detect whether the event target is a text input/textarea (`e.target` is `INPUT`/`TEXTAREA`, or `e.target.closest('input,textarea')`). If so, **return early** — do NOT run any game key shortcuts (`e`, `q`, `v`, `n`, `c`, `k`, `b`, `m`, `+`, `-`, `Escape` game closes). The input's own `keydown` listener (Enter to send, etc.) still fires normally.
- **EXCEPTION:** still allow `Escape` to blur the focused input / close the modal even when the input has focus (so the user can get out). i.e., `if (targetIsInput && e.key !== 'Escape') return;`.
- Ensure the typing-board input's Enter handler still sends the line, and that clicking the input doesn't immediately get stolen by a game key.

### Verification (add test)
- Focus `#typingBoardInput`, dispatch a `keydown` for `e` → the global handler does NOT toggle the projector modal; the input value becomes 'e'.
- Dispatch `Escape` while focused → input blurs / modal closes.
- Confirm the same guard covers `#presenterTopicInput` and the drink-station name input.

## Item 4 — Coffee/drink never lets go after it's done

2. **Sip/consume only clears `heldDrink`, not the visual `heldItem`** and not the carry HUD, so the cup can keep rendering.
3. **Remote players:** `net.js` (line ~206-207) syncs `remote.heldDrink`/`remote.isSipping` from the `move` message; if the local player clears `heldDrink` but the `move` message still carries the old item, or the sprite field differs, the remote avatar can keep holding the cup.

Keep `heldDrink` as an alias or remove it — pick one source of truth and use it everywhere (local render line ~987, remote render line ~971, `updateCarrySlotUI`, `sipDrink`, vending/fridge/coffee-maker assignment, `net.js` `sendMove` payload line ~74-86 and the remote receive line ~206-207).
- **When a drink is consumed** (`sipTimer` expires, line ~792-801): clear the carried item (`heldItem = null`), clear `isSipping = false`, update the carry HUD, AND send a `move` (or dedicated) update so remote players also drop it.
- **Sipping animation** ends cleanly: `isSipping` false + item gone.
- Verify vending, fridge, and coffee-maker all set the SAME unified field.

### Verification (add test)
